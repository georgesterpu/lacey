# Scheduled-check incident, 17 November 2026

The deployed build passed its original release gate. Subsequent scheduled jobs
failed for three separate reasons; a passing build did not prove later imports
and third-party image requests would remain healthy.

- A delayed GitHub event reused a morning scan more than six hours old. Email
  planning correctly refused it. A completed stale slot now recollects the feeds
  before delivery, retaining its run/digest identity and recommendation receipts.
  Freshness uses the actual successful completion time, without altering the
  historical start time or widening the six-hour window. Tests prove that old
  data alone still cannot authorize delivery and that the refreshed slot cannot
  send duplicate digests.
- MisterRunning's page-two navigation failed, but the same page parsed correctly
  in a subsequent cloud diagnostic. Wrong cached page bodies and invalid
  navigation now retry the same checkpoint within the existing three-attempt
  bound. Category requests ask for cache revalidation. Known advertising tags
  are removed; unexpected functional queries and backwards navigation remain
  errors. Failure details include the requested page and next-link query keys.
  Product identity and country checks remain unchanged.
- The resumed crawl exposed a second, reproducible listing bug: single-colour
  cards lack the colour-selector price attributes. Page six had real products
  but none of those attributes. Discovery now parses the scoped product grid
  and colour links, deduplicating URLs. Card prices select candidates only;
  product-page EUR price, size, stock and reference checks control publication.
  The live audit parsed all 32 men's and 31 women's pages successfully.
- Life Style's image server returned HTTP 403 to both the GitHub HTTP client and
  Chrome, although the same images loaded locally. This was a real provider
  access failure. Life Style, Warehouse and Sports Direct are operator-paused
  pending permitted access; their offers are not advertised as current. Healthy
  shops continue independently. No image assertion was removed or relaxed.

The delivery recovery also encountered Shopify HTTP 429 from the worker network.
For temporary transport/throttling failures, an existing published browsing
snapshot may remain visible as **Update delayed**, with its original check time
and unchanged 30-hour expiry. The failed database source stays excluded from
private matching and delivery; cached prices cannot authorize email delivery.
Known bad product checks still remove their products, invalid data is not
published, and operator-paused shops stay hidden. Cached source reports stop
same-slot recollection and repeated calls after the attempt limit. Unexpected
source failures still fail the job. Other eligible shops may deliver only after
the existing fresh per-product verification.

Operator pauses use `ops:source-pause:<source>` keys in `app_state`. Both small
and paged collectors honor them without requests or advancing check timestamps.
Before removing a pause, verify product/size/country access and actual image
loading on the collection worker, then require a successful fresh publication.

The browser check now scrolls a real card into view before testing its lazy
image and captures source/image diagnostics plus a screenshot on failure.
It still requires a real loaded image for every publishing shop.

Manual workflow recovery can use `delivery_only=true` for the small-source
refresh/delivery/backup phase, or `catalogue_only=true` with an existing run ID
to resume a paged collector without emails. Do not select both modes.

Release still requires exact-revision CI, native Postgres integration, a staged
write probe and staged/public mobile and desktop checks. Customer watches and
consent are not reset to repair these failures.
